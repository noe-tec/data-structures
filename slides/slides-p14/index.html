  • Explain contains, insert and remove on a splay tree, and what an amortized cost of O(log N) promises.
The problem

Recently used keys are likely to be used again

  • An AVL tree stores a height in every node and checks the whole path after each insertion. Every key stays about log N deep, used or not.
  • In real programs, a key that was just used is likely to be used again soon.
  • A splay tree stores no height. Every access moves that key to the root, so the keys you use stay near the top.
AVL guarantees O(log N) for each operation. Splay guarantees it over a whole sequence, with no balance data per node.

14.1 Splaying

14.1 · Splaying

Every access moves that node to the root

  • A splay tree is a BST with no height and no balance factor. After every access it moves that node to the root with rotations: that move is a splay.
  • The key you just used is at the root, so using it again costs O(1).
  • There are two ways to splay. Bottom-up: find the node, then rotate it up to the root; this is the one we use. Top-down: rotate during the search itself, in one pass (extra material).
A single access may be slow, but any M operations from an empty tree cost at most O(M log N): an amortized cost of O(log N) per operation.

Checkpoint

X is the left child of P, and P is the right child of G. Which case is it, and what does the splay do?

C. Read the path from the top: from G to P is a step to the right (zag), and from P to X a step to the left (zig). The path bends, so X rises twice: first rotate right at P, then left at G. A has the right idea, a bent path, but reads it in the wrong direction: left-then-right is the mirror case. B treats the path as a straight line. A zag-zag needs X and P to both be right children.

Checkpoint

A splay tree is the chain 30 → 20 → 10: each node is the left child of the one before. You access 10 and splay it bottom-up. Which tree do you get?

B. From 30 the path goes left, then left: a zig-zig. First rotate right at 30, then right at 20. A stops after the first rotation. An AVL tree would stop there, but a splay only ends when the accessed node is the root. C is what you get with single rotations, one step at a time: rotate right at 20, then right at 30. That leaves 20 at the bottom.

14.2 · Splaying in code

Each node also knows its parent

A splay climbs from x to the root, so each node stores its parent, like prev in a doubly linked list. Other ways to code it: see the extra material.


// Node: int info; Node* left; Node* right; Node* parent;
// SplayTree, private: Node* root = nullptr;
void replaceInParent(Node* a, Node* b) {   // b takes the place of a
    b->parent = a->parent;
    if (a->parent == nullptr) root = b;               // a was the root
    else if (a == a->parent->left) a->parent->left = b;
    else a->parent->right = b;
}

14.2 · Splaying in code

The AVL rotations, plus the parent links


void rotateRight(Node* a) {       // the left child of a rises
    Node* b = a->left;
    a->left = b->right;           // the middle subtree changes parent
    if (b->right != nullptr) b->right->parent = a;
    replaceInParent(a, b);        // b goes up to the place of a
    b->right = a;                 // a goes down to the right
    a->parent = b;
}
void rotateLeft(Node* a) {        // mirror image: the right child rises
    Node* b = a->right;
    a->right = b->left;
    if (b->left != nullptr) b->left->parent = a;
    replaceInParent(a, b);
    b->left = a;
    a->parent = b;
}

Same three child links as in P13 and no heights to update. The extra lines keep every parent in step.

14.2 · Splaying in code

splay: one loop, six cases

Each case makes the rotations of the six-cases slide, in the same order.


void splay(Node* x) {                   // x rises to the root
    while (x->parent != nullptr) {
        Node* p = x->parent;
        Node* g = p->parent;
        if (g == nullptr) {             // p is the root: one step
            if (x == p->left) rotateRight(p);                     // zig
            else rotateLeft(p);                                   // zag
        } else if (p == g->left) {      // first step to the left
            if (x == p->left) { rotateRight(g); rotateRight(p); } // zig-zig
            else { rotateLeft(p); rotateRight(g); }               // zig-zag
        } else {                        // first step to the right
            if (x == p->right) { rotateLeft(g); rotateLeft(p); }  // zag-zag
            else { rotateRight(p); rotateLeft(g); }               // zag-zig
        }
    }
}
Checkpoint

In splay, x is the left child of p, and p is the left child of g. A student writes rotateRight(p); rotateRight(g); instead of the zig-zig line. What happens?

C. rotateRight(p) lifts x above p; now x is the left child of g, so rotateRight(g) lifts x again. That is the single-rotation method of the chain slide, not a zig-zig. A: the order matters. Rotating at p and then at g leaves p one level deeper than the zig-zig does. B: after the first rotation, g still has a left child: x itself. That is why the program runs and quietly builds the wrong shape.

14.3 Operations

14.3 · Operations

contains: find the last node, splay it, look at the root


Node* lastOnPath(int x) const {         // root is not null
    Node* n = root;
    while (x != n->info) {
        Node* next = (x < n->info) ? n->left : n->right;
        if (next == nullptr) break;     // x is not in the tree
        n = next;
    }
    return n;                           // x, or the last node of its path
}
bool contains(int x) {                  // not const: it changes the tree
    if (root == nullptr) return false;
    splay(lastOnPath(x));               // that node becomes the root
    return root->info == x;
}

If x is not there, a neighbor of x in sorted order ends at the root.

14.3 · Operations

insert: a BST insertion, then splay the new node

14.3 · Operations

insert: hang the new node where the search stopped


bool insert(int x) {
    if (root == nullptr) {
        root = new Node{x, nullptr, nullptr, nullptr};
        return true;
    }
    Node* p = lastOnPath(x);            // x, or where x would hang
    if (p->info == x) {                 // repeated value: no new node,
        splay(p);                       // but it was accessed
        return false;
    }
    Node* n = new Node{x, nullptr, nullptr, p};
    if (x < p->info) p->left = n;       // the link where the search stopped
    else p->right = n;
    splay(n);                           // the new node rises to the root
    return true;
}
14.3 · Operations

remove: splay x, then join its two subtrees

14.3 · Operations

remove: two splays and one link


bool remove(int x) {
    if (!contains(x)) return false;     // if found, x is now the root
    Node* tl = root->left;
    Node* tr = root->right;
    delete root;
    if (tr != nullptr) tr->parent = nullptr;
    if (tl == nullptr) {                // no TL: TR is the whole tree
        root = tr;
        return true;
    }
    tl->parent = nullptr;
    root = tl;                          // TL alone, for now
    splay(lastOnPath(x));               // x > all of TL: its maximum rises
    root->right = tr;                   // the maximum has no right child
    if (tr != nullptr) tr->parent = root;
    return true;
}

Amortized O(log N): a slow step pays for the next ones

extra data per nodenonea heighta parent link (in this code)
  • A long access path is expensive, but the splay shortens it for the operations that follow.
  • Good fit: a few keys get most of the accesses. Poor fit: every single operation must be fast, or several threads search the tree at once.
Checkpoint

A splay tree holds 1,000,000 keys. Which statement about one call to contains is true?

A. The guarantee is amortized: it covers a sequence, not each operation. Insert 1 to 1,000,000 in order and the tree is a chain; the first contains(1) visits every node. B describes an AVL tree. A bound for each operation needs a balance rule, and a splay tree has none. C is true only for the key you just accessed: the second access costs O(1), after the first one paid for the whole path.

Self-study

Other ways to code a splay

  • Top-down, what Weiss codes: it rotates on the way down, in one pass, with no parent links and no stack. The tree is split into L (smaller keys), R (greater keys) and a middle tree, joined at the end.
  • Recursive, the one most often found online: short, but it pairs the path from the top, so the single zig happens low in the tree, not at the root, and some trees differ. A long chain overflows the stack.
  • With a stack of the path: bottom-up with no parent links; the search saves the links it passes.
Read Weiss (2014), § 12.1, "Top-Down Splay Trees": Fig. 12.4 traces a full example. The complete code, SplayTree.h, is on the book's website.
Why it matters today

The same bet, inside AI systems

  • Prompt caching: a model API can keep a recently used prompt prefix ready to resume. In Claude's API the cache lives 5 minutes by default, and each use refreshes it: what you used last is what stays close.
  • Memoized calls: Python's functools.lru_cache keeps the most recent calls of a function. Its documentation says when that pays off: when the most recent calls are the best predictors of upcoming calls.
