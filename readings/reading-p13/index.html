Short trees, fast answers: why a search tree must stay balanced

Data Structures and Algorithms

A contact list exported in alphabetical order. A log where every record is later than the one before. Customer numbers that grow one by one. Data often arrives already sorted, and that is exactly the order a simple search tree handles worst.

A search tree promises to find one item among a million in about twenty steps, but only if the tree is short. So the real question is: how do you keep a tree short when you cannot choose the order of the data?

The trap: a tree that becomes a list

  • Seven keys. Insert 6, 3, 8, 1, 5, 7 and 9 into a binary search tree and you get three tidy rows. Insert the same keys as 1, 3, 5, 6, 7, 8, 9 and each one hangs to the right of the one before: the tree is now a linked list.[1]
  • Ten million records. Weiss works out the cost for a table of 10,000,000 records stored on disk. In the worst case an unbalanced search tree could need 10,000,000 disk accesses to find one record; a balanced AVL tree needs about 25.[2]
A search tree is only as fast as it is short.

The fix: trees that rebalance themselves

A self-balancing tree checks its shape after every insertion. If one side has grown too tall, it changes a few links to lift that side up, and the data stays in sorted order.

  • Inside Linux. The kernel uses red-black trees, one kind of self-balancing tree. One example from its documentation: when programs ask to be woken up later, the timer code keeps those pending requests in a red-black tree. Several other parts of the kernel track their data the same way.[3]
  • Inside C++. std::set offers search, insertion and removal in logarithmic time, whatever the order of arrival. It is usually implemented as a red-black tree.[4]
Use a self-balancing tree when you cannot control the order in which the data arrives.

Did you know?

The name "AVL tree" comes from its inventors, Adelson-Velskii and Landis. It is a binary search tree with one extra rule: at every node, the two sides may differ in height by at most one.[2]

Think about it

  1. You insert the numbers 1 to 1,000 into a plain binary search tree, in increasing order. How many nodes might a search visit? What changes if the same numbers arrive in random order?
  2. A self-balancing tree does extra work on every insertion. When is that work worth it, and when could you skip it?
  3. The AVL rule allows the two sides of a node to differ by one. Why not demand that they are exactly equal? Try to build such a tree with four items.
