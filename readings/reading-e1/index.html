One bit of color: how the maps in your programs stay fast

Data Structures and Algorithms

A dictionary in C++ or Java keeps its keys in order, and it must find any of them quickly, even when the keys arrive already sorted. A plain search tree fails at that: sorted keys turn it into a long chain.

Balanced trees fix this, but balance has a cost. So the question is: what is the least a tree must remember about itself to stay short?

TreeEach node remembersIts strong point
AVLits heightthe shortest paths, so the fastest searches
Red-blackone bit: red or blackfew changes on each insertion or deletion

Where you already use one

  • In C++. GCC's standard library builds set, map, multiset and multimap on a single red-black tree class.[1]
  • In Java. The documentation of TreeMap opens with "A Red-Black tree based NavigableMap implementation", and promises log(n) time for get, put and remove.[2]
Use a red-black tree when you need sorted keys and a worst-case O(log n) for every operation.

The trade

  • In Linux. The kernel has its own red-black tree library. Its documentation compares it with AVL trees: at most two rotations per insertion and three per deletion, in exchange for slightly slower lookups that are still O(log n).[3]
  • A little taller. Four simple rules about the colors keep the height at most 2 log(N + 1): never more than about 40 levels for a million keys.[4]
Red-black trees give up a little search speed to make every update cheap.

Did you know?

Rudolf Bayer invented these trees as "symmetric binary B-trees". The red and black colors came later, from Leonidas Guibas and Robert Sedgewick.[5]

Think about it

  1. If one bit per node is enough to stay balanced, what does an AVL tree gain by storing a whole height?
  2. Your program inserts and deletes all the time, and searches rarely. Which tree would you pick?
  3. Why might a library prefer a tree that changes little on each update?
