One in a million: how software keeps data sorted while it never stops changing

Data Structures and Algorithms

You type three letters and your phone shows the contacts that match. You open a store app and your orders appear by date, picked out from millions of others. Checking the items one by one would be far too slow, and so would sorting everything again each time something new arrives.

Both systems face the same question: how do you keep data sorted while it keeps changing? A sorted array is fast to search and slow to update. A linked list is the opposite. A search tree gives you both.

Search trees: sorted, and still easy to change

In a binary search tree, every item has smaller items on its left and greater items on its right. A search starts at the top and, after each comparison, continues on one side only. Adding an item follows the same path and attaches it at the end, so nothing has to be shifted.

  • C++. std::map keeps its keys sorted, and its search, insertion and removal operations take logarithmic time: a few dozen steps for a million keys. It is usually implemented as a red-black tree, one kind of search tree.[1]
  • Java. TreeMap is documented as "a Red-Black tree based" map. It is sorted by its keys and guarantees log(n) time to get, put and remove an entry.[2]
Use a search tree when the data must stay sorted and it keeps changing.

Databases: trees built for disk

Reading from disk is much slower than reading from memory, so a database wants to touch as few nodes as possible. A B-tree does that by storing many keys in each node: the tree gets wider and much shorter.[3]

  • SQLite. In an SQLite database file, each ordinary table is stored as a b-tree, and each index is another b-tree.[4]
  • PostgreSQL. The CREATE INDEX command builds a B-tree by default. B-trees handle equality and range queries on any data that can be sorted.[5]
Use a B-tree when the data lives on disk and every node you read costs time.

Think about it

  1. A search goes down one step per comparison. If a tree with a million items is about twenty steps deep, how many of the items does a search never look at?
  2. Binary search finds a key in a sorted array of a million items in about 20 steps. Why would you still prefer a tree? Think about what happens when a new key arrives.
  3. A dictionary app must list every word between "tree" and "trie". Why is that easy for a structure that keeps its data sorted, and hard for one that can only answer "is this word here?"
