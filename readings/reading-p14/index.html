The tree that remembers: what you just used stays on top

Data Structures and Algorithms

You replay the same song. You open the same chat twenty times a day. Most of what you ask a computer for, you asked for a moment ago.

So here is the question: should a search tree move what you just used to the top, where it is fastest to find?

What you just used, you will likely use again

  • Inside Windows. Drivers can keep their data in "generic tables", and by default those tables are splay trees.[1]
  • Inside Chrome. V8, Google's JavaScript engine, used a splay tree in its profiler, the tool that measures where a program spends its time. Google then turned that code into a benchmark for JavaScript engines.[2]
A splay tree is fast when a few items get most of the requests.

The cost: one search can be slow

  • It can become a chain. The same Windows page warns that a splay tree can become deep and narrow, even a straight line, and it offers a balanced tree as the alternative.[1]
  • Searching moves things. Every search rotates nodes, so even a read changes memory. The V8 benchmark exists partly to measure that.[2] What a splay tree promises is the total: M operations in a row take at most about M log N steps.[3]
A splay tree is fast over many operations, not on each one.

Did you know?

Splay trees were introduced in 1985 by Daniel Sleator and Robert Tarjan, in a paper called "Self-adjusting binary search trees". The name says it all: the tree adjusts itself to the way you use it.[4]
